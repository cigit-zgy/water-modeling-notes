LaTeX 擅长解决论文“如何排版”，却没有回答论文“如何演化”。一篇稿件从初稿进入投稿、返修、再次投稿到最终归档，研究者需要同时维护当前正文、历史版本、marked manuscript、审稿回复、参考文献、作者信息和投稿附件。只要其中一类状态仍靠文件名、复制习惯或个人记忆维持，返修轮次增加以后就容易出现版本来源不清、产物过期或修改 provenance 丢失的问题。

LLM Agent 的加入进一步放大了这一矛盾。Agent 可以读取和写入文件，也可以调用编译器和脚本，但“能够操作文件”并不等于“获得了修改科学内容的授权”。因此，科研写作自动化首先需要解决的不是让 Agent 更会写，而是让**稿件状态、操作权限和产物关系显式化**。

[`sci-manuscript-skill`](https://github.com/cigit-zgy/sci-manuscript-skill) 就是围绕这个问题设计的。当前正式版本为 [`v2.1.0`](https://github.com/cigit-zgy/sci-manuscript-skill/releases/tag/v2.1.0)。它不负责自动生成论文，而是把初始化、版本演化、返修标记、审稿回复、回滚、重编号、参考文献状态和投稿打包组织成一个可验证的 LaTeX 稿件生命周期。

<AcademicCallout kind="definition">
  本文所说的**稿件生命周期工程（manuscript lifecycle engineering）**，是指为稿件状态、版本关系、修改来源、构建过程和正式产物建立明确契约。它管理科研写作的工程状态，不替代研究者的科学判断。
</AcademicCallout>

## 问题不只是“版本管理”

Git 已经能够保存文件历史，但科研返修还包含 Git 本身并不了解的语义：当前轮次的直接父版本是谁；某个修改是否由 Reviewer 1 的 Comment 2-2 引起；当前 response letter 应该引用 marked manuscript 的哪一处位置；一个旧 PDF 是否仍对应当前源文件；历史轮次能否在今天重新构建出一致结果。

同样，`latexdiff` 能够提供文本差异证据，但它并不知道哪些差异代表当前稿件中应展示的自然修改单元，也不知道修改属于 reviewer 还是作者，更不能单独承担整个稿件生命周期的状态管理。

<ResponsiveTable caption="Table 1. 常见工具能够解决的问题与仍然缺失的稿件语义" variant="striped-minimal">

| 工具或做法 | 能解决什么 | 仍然缺失什么 |
| :-- | :-- | :-- |
| Git | 保存文件历史和 commit graph | 稿件轮次、审稿 provenance、正式产物状态 |
| LaTeX | 确定性排版与交叉引用 | revision ancestry 和返修工作流 |
| `latexdiff` | 提供 parent/current 差异证据 | 科学结构、修改所有权和可读高亮粒度 |
| 手工目录复制 | 快速保留一个快照 | 可验证 ancestry、stale artifact 检测和回滚保护 |
| Agent | 自动执行多步骤操作 | 科学内容授权边界和确定性状态约束 |

</ResponsiveTable>

因此，`sci-manuscript-skill` 的设计目标不是取代这些工具，而是在它们之上增加一层**稿件生命周期语义**。

## 第一原则：科学内容和工程操作分离

系统最重要的约束是：生命周期命令不构成科学内容修改授权。`build`、`revision`、`rollback`、`reindex`、`sync-bib` 和 `submission` 可以改变工程状态，但不能因为 Agent 获得了文件权限，就默认允许它润色正文、改公式、补引用或重写 response。

这使系统形成了一个明确的职责边界：研究者负责论文中的科学论证和科学修改；Skill 负责告诉 Agent 什么可以做、何时必须停止；Python package 负责执行可确定、可检查的机械操作。

<ResponsiveTable caption="Table 2. sci-manuscript-skill 的核心职责边界" variant="striped-minimal">

| 对象 | 主要责任 | 不应该承担的责任 |
| :-- | :-- | :-- |
| 研究者 | 科学判断、正文、图表、回复内容 | 手工维护所有构建状态 |
| `SKILL.md` | 请求路由、授权边界、fail-closed 规则 | 直接实现底层文件操作 |
| Python package | 生命周期、构建、验证、状态与产物 | 自行决定科学内容 |
| LaTeX / TeX state | 排版、编号、引用、位置和执行状态 | 判断科学内容为什么改变 |
| PDF | 最终阅读与交付 | 反向定义科学状态 |

</ResponsiveTable>

这也是项目和普通“自动写论文 Agent”的主要区别：自动化对象首先是**工作流本身**，而不是研究者的科学判断。

## 两层架构：Skill 约束 Agent，package 执行确定性操作

项目将 Agent 行为和程序执行拆成两层。`SKILL.md` 是面向 Agent 的入口，规定请求应路由到哪个操作、哪些内容未经授权不能修改，以及出现歧义时应该继续还是停止。安装后的 `sci_manuscript` package 则提供 CLI 和 Python API，并集中实现 workspace、metadata、revision、compile、diff、response、submission 和状态验证。

这种分层避免了两个问题。第一，Agent 不需要自己临时发明目录规则或版本语义；第二，命令行与 Agent 调用复用同一套 domain logic，不会逐渐演变成两套互不一致的实现。

```text
Agent request
    ↓
SKILL.md / references       # 行为约束与 progressive disclosure
    ↓
CLI / ManuscriptProject     # 稳定执行入口
    ↓
domain logic                # lifecycle / revision / response / validation
    ↓
TeX + package resources     # 确定性构建
    ↓
user-facing artifacts
```

## 工作区只保存研究者真正需要管理的状态

`sci-manuscript-skill` 不接管整个科研项目，而是在项目中维护 `manuscript/` 工作区。当前结构的重点不是“每轮复制一切”，而是把**可编辑源、冻结状态、运行诊断和正式产物**分开。

```text
project/
└── manuscript/
    ├── references/             # 当前 BibTeX 与 revision style
    ├── initial_submission/     # r00
    ├── revision_01/            # r01
    ├── revision_02/            # r02 ...
    ├── state/                  # manifest 与冻结历史状态
    └── tmp/                    # TeX/AUX/log/cache/audit 等运行信息
```

每个正式轮次都有自己的科学源和输出状态，但 publisher class、response template 和 revision runtime 等基础设施由安装后的 package 提供，不需要复制到每篇论文里。最终用户面对的 `output/` 只保存当前有效的 PDF；TeX、AUX、日志、timing 和审计信息留在 `tmp/`。

## 生命周期：相邻 revision，而不是任意版本跳转

一篇稿件从 `initial_submission` 开始，内部记为 `r00`。进入返修后，`revision_01` 的 parent 是 `r00`，`revision_02` 的 parent 是 `revision_01`。这种相邻 ancestry 看起来保守，但它让“当前修改相对于谁”只有一个答案。

`--round` 可以选择已有历史轮次进行构建，但不会静默改变 active round；不存在的 round 会显式失败。历史轮次在构建前还会检查被冻结的源文件、参考文献、作者信息和 ancestry 状态，避免“今天的共享文件”悄悄改变“昨天的投稿版本”。

## 最关键的变化：marked manuscript 不再等于 raw diff

早期版本最容易犯的错误，是把文本 diff 直接等同于高亮结果。实际稿件中，一个 source line break、段落顺序变化、公式移动，甚至 surrounding context 的改变，都可能让纯文本 matcher 产生错误的 visual change。对于返修稿，这种 false positive 会直接误导作者和审稿人。

v2.1.0 将这一过程改成结构感知、identity-first 的 revision pipeline。核心原则可以概括为：

```text
STRUCTURE
→ IDENTITY
→ MATCH / CHANGE PROOF
→ PROVENANCE
→ PRESENTATION
→ TEX-NATIVE VERIFICATION
```

其中最重要的是顺序：**先证明一个自然单元是否仍然相同，再决定是否需要高亮；只有已经证明发生变化的内容，才进入 provenance 和 presentation。** 句子切分只决定“已经变化以后染多大”，不能决定“有没有变化”。

<AcademicCallout kind="method">
  `sci-manuscript-skill` 对 revision highlighting 采用 fail-closed 策略：匹配失败或上下文歧义本身不能授权颜色。没有正向 change evidence，就没有 revision color。
</AcademicCallout>

这套规则不仅用于普通段落。normalized-identical 的 display equation 即使移动位置也保持黑色；figure asset 变化不会借用未变化的 caption 作为视觉代理；citation、DOI 和 URL 则作为受保护的 inline unit 保留独立呈现。

## 为什么需要“proof-carrying highlighting”

为了避免“Python 认为改了”和“TeX 实际染了”之间再次出现隐式路径，v2.1.0 把 visible revision 进一步组织成带证明的状态链。

系统内部区分四类信息：

<ResponsiveTable caption="Table 3. revision rendering 中的四类证明与事件" variant="striped-minimal">

| 状态 | 证明什么 | 对最终高亮的影响 |
| :-- | :-- | :-- |
| `IdentityCertificate` | parent/current 自然单元保持一致 | hard veto，保持黑色 |
| `ChangeCertificate` | current unit 确实 changed 或 added | 才有资格进入 revision color |
| `StructuralEvent` | 发生移动、asset change 等结构事件 | 不自动产生视觉高亮 |
| `RenderCertificate` | TeX 实际执行了已授权 revision event | 与 `ChangeCertificate` 一一核对 |

</ResponsiveTable>

renderer 不再可以随意输出一个红色或绿色 span。每个可见 revision event 都需要确定的 event ID；TeX 编译过程中，package-owned macro 会把实际执行事件写入轻量 `.sci` sidecar。编译结束后，Python 预期的 change registry 与 TeX 实际执行 registry 必须一致，否则构建失败。

这种设计的目的不是增加复杂度，而是消除一种危险的隐式逻辑：**“因为 matcher 不确定，所以先染出来再说。”** 在科研返修中，不确定性更适合触发显式错误，而不是被转换为视觉事实。

## 修改来源：WHAT 必须先于 WHO

返修时还要区分“改了什么”和“为什么改”。项目只使用 `\review{ID}{...}` 描述 reviewer provenance：

```latex
\review{2-2}{The current text revised in response to Reviewer 2, Comment 2.}
```

这里的 `\review` 只回答“如果这段内容确实发生变化，它属于哪个 reviewer comment”。它不会自动把 wrapper 里面的全部文字染色。若 parent/current 内容完全相同，即使 current source 被 `\review{...}` 包裹，也仍然保持黑色。

作者主动修改不需要另一套 `\user` wrapper：**不属于 reviewer provenance、但被 change proof 确认为当前修改的内容，即为 author-driven change。** 这使 WHAT 和 WHO 保持分离，也避免为了视觉效果在科学正文里堆积越来越多 markup。

当前 marked manuscript 的 presentation contract 是：

<ResponsiveTable caption="Table 4. v2.1.0 marked manuscript 的视觉语义" variant="striped-minimal">

| 当前内容 | 最终表现 |
| :-- | :-- |
| Reviewer / Editor 驱动的当前新增或替换 | `RubineRed` |
| 作者主动的当前新增或替换 | `ForestGreen` |
| 未变化科学内容 | black |
| citation marker、DOI、URL | xcolor 原生 `blue` |
| parent-only deletion | 不显示 |

</ResponsiveTable>

这里有一个容易忽略但很重要的定义：**marked manuscript = current clean manuscript + revision highlighting**。它不是 forensic diff，也不展示已经从 current source 删除的 parent-only 内容。

## Source、TeX、State 和 PDF 各自负责什么

另一个容易引发错误的设计是从最终 PDF 反向推断正文、编号或 response correctness。PDF 是排版后的结果，文本提取顺序、字体编码和页面几何都可能受模板影响，因此它不适合作为科学状态 authority。

v2.1.0 将 authority 明确拆成四层：

<ResponsiveTable caption="Table 5. 构建过程中不同状态来源的权威边界" variant="striped-minimal">

| Authority | 负责的状态 | 不负责什么 |
| :-- | :-- | :-- |
| Source | 科学内容、结构、parent/current 比较 | 页面坐标和最终排版 |
| TeX | labels、citations、bibliography、line locations、package events | 判断修改为什么发生 |
| State | round ancestry、冻结历史、artifact freshness | 重写科学内容 |
| PDF | 最终阅读、视觉检查和交付 | 反向定义 revision / response 科学正确性 |

</ResponsiveTable>

因此，response location 使用 `lineno` 与 AUX labels 获取；编号、引用和 bibliography 状态来自 TeX 中间状态；response 的关键执行事件也通过 TeX sidecar 验证。PDF 仍然需要做最终视觉 QA，但它不再反馈到 change detection 或 scientific-state 判断。

## Response letter 也是 lifecycle 的一部分

每轮 revision 有自己的 reviewer comments 和 `responses.tex`。作者为每条 detailed comment 填写一个 `\Response{ID}{...}`；如果 reviewer 确实导致 reference addition 或 metadata change，还可以使用 `\ReviewReference` 建立 causal provenance。

Response letter 的 opening、correspondence block 和签署结构由 package-owned template 统一生成，正文回复仍由研究者控制。当前 line location 从最终 marked source 的 TeX-native state 得到，而不是从 PDF bbox 反推。

这使 response 不再是一个和正文分离的 Word/TeX 文件，而是能够与 comment ID、manuscript provenance、line location 和当前 revision 共同接受 audit 的正式 artifact。

## 回滚、重编号和历史可复现性为什么必须保守

生命周期系统中最危险的操作不是创建新文件，而是删除、回滚和重编号，因为它们可能改变已经形成的科研历史。

因此 `rollback` 和 `reindex` 都要求显式确认，并在变更前保存 archive；历史轮次还会使用冻结状态验证 source、bibliography、authors 和 ancestry。构建 manifest 同时将正式 artifact 标记为 `CURRENT`、`STALE` 或 `MISSING`，输入发生变化后不会继续把一个旧 PDF 当作当前结果。

这套设计的目标不是追求“自动修复一切”，而是让危险状态尽早暴露。对于无法唯一解析的 duplicate/context、部分复杂数学定位环境和不满足 contract 的历史状态，系统宁可 fail closed，也不静默猜测。

## 最小使用流程

安装后先检查环境：

```bash
git clone https://github.com/cigit-zgy/sci-manuscript-skill.git
cd sci-manuscript-skill
python -m pip install .
sci-manuscript doctor
```

初始化稿件并构建初稿：

```bash
sci-manuscript init --project /path/to/paper
sci-manuscript build --project /path/to/paper
```

收到审稿意见后创建下一轮：

```bash
sci-manuscript revision --project /path/to/paper --yes
```

研究者显式修改正文和 response 后，可以只构建 marked manuscript，也可以执行完整交叉验证：

```bash
sci-manuscript build --project /path/to/paper --target marked
sci-manuscript build --project /path/to/paper --target all
```

常用 build target 的含义如下。

<ResponsiveTable caption="Table 6. revision round 的主要 build target" variant="striped-minimal">

| Target | 主要工作 |
| :-- | :-- |
| `clean` | current source + bibliography → clean PDF |
| `marked` | parent/current comparison → marked PDF |
| `response` | 获取当前 marked state、位置并构建 response letter |
| `all` | clean + marked + response + cross-artifact validation |

</ResponsiveTable>

如果需要撤销误创建 revision 或整理编号，可以分别使用 `rollback --yes` 和 `reindex --yes`。这些命令属于破坏性 lifecycle 操作，因此不会像普通 build 那样静默执行。

## 当前验证与边界

v2.1.0 的发布门禁包括 Python 单元/集成测试、真实 LaTeX 工具链、clean-wheel 安装与资源检查，以及完整稿件 parent/current gold-pair 的 revision truth audit。该 gold pair 中的 false positive、false negative 和 ambiguity 均为 0；这个结果证明的是**该验证对象与当前测试边界内的实现正确性**，而不是宣称任意 LaTeX 稿件都不存在未来 bug。

<AcademicCallout kind="caution">
  当前 revision scanner 是保守的 TeX-aware scanner，而不是通用 LaTeX AST；没有 fuzzy move detection、语义 NLP parser 或数学 AST。无法唯一证明的情况会 fail closed。Tectonic 拥有最完整的集成验证证据，传统 LaTeX toolchain 仍依赖本地安装环境。
</AcademicCallout>

这种限制是有意的。对科研基础设施而言，一个明确拒绝不确定输入的系统，通常比一个试图“聪明地猜完所有情况”的系统更容易审计。

## 这套设计最终解决的是什么

`sci-manuscript-skill` 最终并不是给 LaTeX 增加更多命令，而是把原本隐含在研究者习惯中的状态外显出来：版本有明确 ancestry，修改有明确 provenance，正式 artifact 有 freshness，revision color 需要 change proof，TeX 执行需要 render proof，历史轮次有冻结状态，Agent 操作有权限边界。

因此，LLM Agent 在这个工作流中的角色也更清楚：它可以成为一个执行者，但不应该成为隐式的科学内容所有者。真正值得自动化的，是那些能够被定义、检查和恢复的科研工程操作。
